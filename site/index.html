数据是怎么来的，以及它测不到什么

  1. 主证据是「条数」，只用四条能落地的路子。① 实测产物：读项目自己发布的文件（小程序数据包、App 的 entries.json、数据集的 stats.json、站点自带的数据文件…），按上游官方口径（book/*.md 里的 ### 标题数）数出真实条数；② fork 对比：它若是上游 fork，直接逐文件数它的 book/*.md；③ 逐条页清单：很多静态站给每条内容都生成了一个独立页面，数 sitemap 里的逐条页即可；④ 运行时：读源码确认它每次打开都直接向上游取最新正文 → 不存在「落后」，从落后名单里剔除。每行用的哪条路子，都写在表里。
  2. 为什么不拿「逐字比对正文」当主证据。我们试过用上游条目标题原文去各站做精确匹配，14 项里 13 项 0 命中 —— 因为各站普遍会改写标题。真正能比的是站点的数据文件（比如 howtolivebetter.net 把正文完整打在 book-index-*.js 里，对上游标题 684/685 = 99.9% 命中），但每个站的数据文件位置都不一样，得逐站定制，通用性差。所以本页把「条数」作为主证据，逐字比对只在个别站点做交叉验证。
  3. 「落后多少条」用上游官方口径复算过。上游条目数由 git log -p -- book/ 逐次累积统计得出（本机复算 690 条，共 409 次提交），再与各版本的实测/自述条数相减。两个输入都能独立复核。
  4. 「落后 N 天」有粒度盲区。690 条是某天某一刻达到的，而当天很多提交只改文档、不改条数。所以我们优先用站点自己声明的构建 / 修订时间（构建产物时间、更新记录页、App 版本发布日期），拿不到才退回 sitemap 的 lastmod，再拿不到才用「该条数首次出现在上游的时间」。准确说法是：「若内容停在达到 N 条的那次提交，则大约落后 N 天」。要更准只能逐站 diff 正文。
  5. 「运行时自动跟进」是读了源码得出的，不是我们替它保证的。例如 daily-life-tip 的 RemoteBook.swift 里写着「内置的那份数据是编译时快照，永远能出内容。这里只负责『书更新了，跟上去』」；shiye-tab 的 src/sources.js 每次打开都拉 raw.githubusercontent.com/eternity4719/… 并按 ### 解析。这类版本不该被算作「落后」。
  6. 「自述」和「实测」在表里是分开的。实测 = 读它自己发布的文件数出来的真数；自述 = 只有它自己写的数字可参考。目前 17 项里有 14 项拿到了实测依据；剩下 1 项是 iOS App，只能读商店页文案 —— App 的条目数不下载安装包就测不了，这是诚实的边界，我们不会拿自述当真数。
  7. 「门槛」一列照抄上游 衍生项目.md 的原文口径，标「未标注」= 原文也没写，非本站核验。可达性、延迟、CDN、条目数为本站实测。
  8. 可达性是单机单时点结论。Cloudflare 站在国内「时通时不通」，探活全通只说明此刻通畅。
  9. 本页不转载正文、不开评论区。正文版权归上游及各衍生作者，有出入时以 上游中文原文 为准（CC BY 4.0）。
  10. 数据是活的，但不是秒级。本站 Worker 每次请求会去上游取一次最新条目数（边缘缓存 10 分钟）；完整的逐项重算由 GitHub Actions 每天跑一次，结果回灌进本站的数据层，页脚会显示上次重算时间。
