方法与局限（先读这段再信上面的表）

  1. 只用四条「能落地」的路子，不猜。① 实测产物：读项目自己的产物文件（小程序 bundle、App 的 entries.json、数据集的 stats.json…），按上游官方口径（book/*.md 里的 ### 标题数）数出真实条数；② fork 对比：它若是上游 fork，直接逐文件数它的 book/*.md；③ sitemap：读 sitemap.xml 的 lastmod 与 URL 数（弱信号）；④ 运行时：源码级确认它每次打开直接拉上游原文 → 不存在「落后」，从落后名单里剔除。每行的依据都写在表里，实测与页面自述严格分开。
  2. 内容级探针试过了，结论是这条路不通，如实报告。我们用上游最近 14 次提交新增的 33 条条目标题原文，去各站实际内容里做精确匹配，13/14 项 0 命中。定向诊断查出两个互相独立的原因：① 衍生站普遍改写标题（上游「家里老人遛狗，把牵绳握在手心……」在站上只剩「家里老人」能匹配）；② 更根本的是正文压根不在页面或主 bundle 里 —— howtolivebetter.net 的 638 KB bundle 对上游前 60 条老条目 0/60 命中，说明它按需分块或运行时拉取，抓 <script src> 根本碰不到正文。所以本页不拿探针当证据。
  3. 「落后多少条」用官方口径复算过。上游条目数由 git log -p -- book/ 逐次累积统计得出（本机复算 687 条，共 398 次提交），再与各项目的实测/自述条数相减。两个输入都能独立复核。
  4. 「落后 N 天」有粒度盲区。687 条是某天某一刻达到的，但当天很多提交只改文档、不改条目数。准确说法是：「若内容停在达到 N 条的那次提交，则内容落后 N 天」。要更准只能逐站 diff 正文，本轮没做。
  5. 「运行时自动跟进」不是我们替它保证的，是读了源码。例如 daily-life-tip 的 RemoteBook.swift 里写着「内置的那份数据是编译时快照，永远能出内容。这里只负责『书更新了，跟上去』」；shiye-tab 的 src/sources.js 每次打开拉 raw.githubusercontent.com/eternity4719/… 并按 ### 解析。这类项目不该被算作「落后」。
  6. 「无版本信号」不代表内容旧。它只代表该站没有提供任何可核验的版本信号 —— 这本身就是本页要暴露的问题。
  7. 「门槛」一列照抄上游 衍生项目.md 的原文口径，标「未标注」= 原文也没写，非本站核验。可达性、延迟、CDN、条目数均为实测。
  8. 可达性是单机单时点结论。Cloudflare 站在国内「时通时不通」，探活全通只说明此刻通畅。本站不托管任何正文，只做指路。
